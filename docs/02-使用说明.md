# tgg-escrow 使用说明

> 这份讲的是「系统跑起来之后，它有什么功能、怎么用」。从一笔交易怎么走完、机器人有哪些命令、
> Mini App 干什么活、管理端有哪些接口，到风控、争议、费用、对账、升级，全都在这。
> 里面的命令写法跟机器人实际回你的一模一样，照着用就行。

---

## 第 0 章 谁在用什么

| 谁 | 平时在哪操作 |
|---|---|
| 买方 / 卖方 | Telegram 私聊机器人（发命令）+ **Mini App**（需要钱包签名的链上动作）+ 交易群 |
| 运营 / 管理员 | 管理接口（`/admin/*`，Basic 认证）+ 心跳脚本 + 链上浏览器（tonviewer/tonscan） |

三个操作面的分工，记住一句话就够：**机器人的命令负责「记一笔」，钱包签名才负责「钱真的动」**。

- **Bot 命令**：建单、流程推进的登记（锁仓/交付/放款/退款这些先记账）、查询、争议、评价；
- **Mini App**：连接钱包后的**链上动作**——部署合约、放款、退款、争议退款、逃生票投票，
  每一笔都要用户自己钱包签名；
- **管理接口**：对账、催办、升级治理、争议卷宗与裁决执行、费用台账，这些运营动作。

> 看到命令回执里写「链上操作请在 Mini App 完成」的，意思就是：打开 Mini App，用钱包签名。

## 第 1 章 一笔交易怎么走完

```
  create（预览）→ confirm（创建）
        │
        ▼
      OPEN（已创建，待卖方确认）
        │  卖方 accept（或通过邀请链接进入）
        ▼
    CONFIRMED（卖方已确认，待买方托管）
        │  买方 lock（登记）＋ Mini App 链上部署合约并注资【签名】
        ▼
     LOCKED（资金已托管在链上合约）
        │  卖方 deliver（交付登记）
        ▼
    DELIVERED（已交付，待买方验收）
        │  买方 release（放款登记）＋ Mini App 链上放款【签名】
        ▼
    RELEASED（已放款给卖方，终态）

  中间还能走这些岔路：
  · cancel   —— 仅当事人、且资金还没锁仓时可以取消 → CANCELLED（终态）
  · refund   —— 协商退款（先登记）；真正的链上退款在 Mini App 里执行
  · dispute  —— 发起争议 → DISPUTED（自动流程暂停，进入陈述/证据/裁决）
                  → 裁决执行（放款或退款）或逃生票退款
  · 退款完成 → REFUNDED（终态）
```

每一步只要有一方动了，对方都会收到机器人通知，随时可以用「订单卡片/状态查询」复核。
订单号就是数据库自增号——不想记的话，`/escrow my` 列出来给你挑。

## 第 2 章 机器人命令全集

> 在群里用：先**回复对方的消息**，再发 `/escrow create <金额> <币种>`，这样不用输对方 ID；
> 私聊里用，就需要把 `<卖方ID>` 写上。

### 2.1 创建与接单

| 命令 | 说明 |
|---|---|
| `/escrow invite <金额> <币种>` | **生成邀请链接**：发到群里或私聊给对方，点开即接单。适合「你先发链接，对方一键进来」。 |
| `/escrow create <卖方ID> <金额> <币种>` | **风险预览**：先跑一遍准入和风控预检（并发/冷却/信用分层等），把风险提示给你看，**并不真的建单**。 |
| `/escrow confirm <卖方ID> <金额> <币种>` | **正式创建**（预览的下一步）：建单并通知卖方确认。二次确认窗口默认 5 分钟。 |
| `/escrow accept <单号>`（卖方） | 卖方确认接单（点邀请链接进来的，流程会自动走到这步）。 |

### 2.2 资金流程

| 命令 | 说明 |
|---|---|
| `/escrow lock <订单号>` | **买方托管登记**：把订单标记为进入锁仓流程；真正的链上部署合约和注资在 Mini App 里做（钱包签名）。 |
| `/escrow deliver <订单号>` | **卖方交付**：标记已交付（发货凭证之类的可以另外发给对方）。 |
| `/escrow release <订单号>` | **买方验收放款**：先登记放款意向；链上放款在 Mini App 签名执行。 |
| `/escrow refund <订单号> [理由]` | **退款**：任一方都能发起协商退款（链下先登记），链上退款在 Mini App 执行；已经进入争议的退款走裁决轨道。 |
| `/escrow cancel <订单号>` | **取消订单**：仅当事人可用，且**资金还没锁仓**。 |

### 2.3 查询与榜单

| 命令 | 说明 |
|---|---|
| `/escrow status <订单号>` | 看订单当前状态、金额、双方，以及下一步能做什么。 |
| `/escrow my` | 列出你参与的交易（最新的在前，不用记单号）。 |
| `/escrow rank [条数]` | 交易榜（默认 10 条）。**默认脱敏**，不显示完整用户 ID。 |
| `/escrow credit` | 看**自己的信用摘要**（成交、争议、履约这些维度）。 |
| `/escrow credit @用户名` | 看**对方公开出来的信用维度**——对方公开了哪些就显示哪些。 |
| `/escrow publish [--detail <维度>]` | **公开你的用户名**到榜单（可以只开放某个信用维度；默认全程脱敏）。 |
| `/escrow unpublish` | **关闭公开**（榜单和信用维度一起收回）。 |

### 2.4 争议与评价

| 命令 | 说明 |
|---|---|
| `/escrow dispute <订单号> <理由>` | 发起争议：订单进入 DISPUTED，自动流程暂停，进入「陈述 → 已读 → 举证 → 裁决」轨道。 |
| `/escrow statement <订单号> <陈述>` | 提交争议陈述（争议中，**每方限一条**）。 |
| `/escrow read <订单号>` | 阅读并确认已读对方陈述（裁决的前置条件之一）。 |
| `/escrow evidence <订单号> <证据>` | 提交争议证据（争议中、**举证窗口内**，走双通道提交）。 |
| `/escrow review <订单号> <评分 1-5>` | 评价：仅限**终态**交易，双方各一次。 |

### 2.5 交易群和其它

| 命令 | 说明 |
|---|---|
| `/escrow guide` | 交易群创建引导（建群 → 拉人 → 群内落单的推荐做法）。 |
| `/escrow`（不带子命令） | 回你一份**全量命令清单**（第 2 章的浓缩版）。 |
| `/start` | 欢迎语和快速引导。 |

> 命令参数忘了也没关系——机器人只会回你刚碰的那条命令的用法，并告诉你去看 `/escrow`。

## 第 3 章 Mini App（干链上活的台子）

### 3.1 怎么打开

- Telegram 的菜单按钮（管理员在 @BotFather 里配了 `TGG_WEBAPP_URL` 后出现）；
- 或者从机器人回执里的「打开表单」按钮进去。

### 3.2 主页面

打开后能看到：你的订单列表（最近的）、每一单**当前可用的动作按钮**（随订单状态变）、
钱包连接（TON Connect）。**所有要动钱的操作都在这里发起**：

| 动作 | 什么时候出现 | 要不要签名 |
|---|---|---|
| 部署托管合约并注资 | CONFIRMED（买方） | 要（部署+转账一笔搞定） |
| 链上放款 | DELIVERED（买方） | 要 |
| 链上退款 | LOCKED / 争议等（看状态） | 要 |
| 逃生票投票 | 合约正在升级提案冷静期、且治理异常时 | 要（双方各一票 = 全额退款） |
| 看订单链上状态 | 任何时候 | 不用（只读） |

> 按钮显示哪些，由后端的 `order-actions` 接口决定——**按钮出现，就说明这个动作现在对你这方开放**；
> 点了之后链上失败的话，页面会告诉你原因（余额不够/网络/合约状态等）。

### 3.3 退款工具页（独立页面）

有一个不依赖机器人的退款入口（`/refund/`），专门给「机器人挂了的兜底场景」用：
连钱包 → 选订单 → 发起链上退款。跟主页面共用同一套合约接口，安全性一致。

### 3.4 常见问题

- **打开是白屏**：域名必须 HTTPS；再检查反向代理有没有把原始查询串原样转发（initData 校验对 query 敏感）。
- **一直提示签名失败**：钱包的网络要和应用一致（测试网对测试网、主网对主网）。
- **订单不显示**：确认是不是用**同一个 Telegram 账号**打开的（Mini App 靠 initData 认人）。

## 第 4 章 管理功能（/admin 接口全表）

所有接口走 **Basic 认证**（`TGG_ADMIN_USERNAME/PASSWORD`），示例统一写 `curl -u "$U:$P"`。
**建议只从服务器本机或内网调用**（要外访就经 HTTPS 反代再加一层 IP 白名单）。

| 接口 | 方法 | 用途 | 示例 |
|---|---|---|---|
| `/admin/reconcile` | POST | **批量对账**（不带 orderId）或单笔对账（带 `{"orderId":N}`）：把链上领先的状态回填；有 DANGER 会主动推给管理会话。单笔撞上并发冲突会明确返回 409。 | `curl -u $U:$P -X POST http://127.0.0.1:8080/admin/reconcile` |
| `/admin/notify-timeouts` | POST | **超时提醒巡检**：对超期还没提醒过的订单，给买方推一键深链提醒（不动链上资金）。 | 同上，换个路径 |
| `/admin/ops-alert` | POST | 运维告警注入口：脚本发现异常时把告警投到管理会话（通知文案由应用统一）。 | `-d '{"text":"..."}'`（按接口契约） |
| `/admin/upgrade` | POST `/propose` `/apply` `/cancel` `/broadcast`；GET `/status` | **合约升级治理**：提案/应用/取消/双通道广播/查状态。 | `POST /admin/upgrade/propose`（body 见表后说明） |
| `/admin/pause` | POST（暂停）/ `/unpause` / `/broadcast` | **全局暂停开关**（治理出问题时的保险）：暂停交易入口并广播。 | `curl -u $U:$P -X POST .../admin/pause` |
| `/admin/verdict` | POST（立案裁决）；`/chain-retry` `/chain-execute` `/chain-cancel` | **争议裁决**：形成结论 → 链上执行/取消/重试（三方签名流程）。 | `POST /admin/verdict`（body：orderId、outcome 等） |
| `/admin/dispute-case` | GET（`?orderId=`） | **争议卷宗**：看某单的争议会话、陈述、证据、时间线。 | `curl -u $U:$P ".../admin/dispute-case?orderId=1"` |
| `/admin/fee-ledger` | GET（列表）；POST `/settle` | **费用台账**：平台/裁决/联邦分成的记账与结算。 | `GET .../admin/fee-ledger` |
| `/admin/chain` | GET `/own-jetton-wallet`；POST `/deploy` | 链上运维：查本部署的 jetton 钱包；跑腿手动部署（对账用）。 | `POST .../admin/chain/deploy`（body 同 reconcile 契约） |

> **升级治理接口的细节**：`propose` 要带新代码哈希/来源（按接口契约），`apply` 要等 72 小时
> 冷静期满才能生效，`cancel` 撤回还没生效的提案。**合约里的逃生票**（两票齐=全额退款）
> 独立于管理端，是用户手里的最终保险，可以绕过任何运营方动作。管理端 `upgrade/status`
> 能看到每个合约的提案哈希和倒计时。

## 第 5 章 风控、准入与信用

### 5.1 交易准入（下单时自动检查）

下 `create`（预览）或 `confirm`（创建）的时候系统会自动查这些，不过就明确拒绝：

| 检查 | 说明 | 相关配置 |
|---|---|---|
| 并发上限 | 同一人在途交易数上限（防刷） | `TGG_TRADE_CONCURRENT_MAX` |
| 冷却 | 两笔交易之间的最小间隔 | `TGG_TRADE_COOLDOWN` |
| 信用分层 | 按信用分决定「直接交易 / 需二次确认 / 拒绝」 | `TGG_TIER_NORMAL_MAX` / `TGG_TIER_CONFIRM_MAX` |
| 惩罚加严 | **争议败诉 ≥2 次 → 暂停其投票类动作；≥3 次 → 交易限制与冷却加严** | 内置规则（见下） |
| 币种白名单 | 只允许配置里的币种 | `TGG_ALLOWED_CURRENCIES` |

### 5.2 惩罚规则（用户能看懂的版本）

- **败诉 ≥2 次**：投票暂停（不能参与治理表决类动作）；
- **败诉 ≥3 次**：交易限制加严 + 冷却期拉长（准入收紧）；
- **可疑标记**（风控命中）：账号公示（出现在公开面）。

> 「败诉」怎么算：裁决结果对你不利，你就是败诉方。比如「放款给卖方」这单，买方就是败诉方。

### 5.3 信用维度与榜单

- `TGG_CREDIT_WEIGHTS` 启用后，系统按权重算信用摘要（成交数、履约、争议这些维度）；
- **信用是用户自己的数据**：默认全脱敏；用户可以用 `/escrow publish` 选择性公开（甚至只开一个维度）；
- `/escrow unpublish` 一键收回；
- 周榜推送（`TGG_CREDIT_WEEKLY_PUSH`）会把榜单推到交易群（默认匿名）。

## 第 6 章 争议与裁决（整条流程）

```
争议发起（任一方）:  /escrow dispute <订单号> <理由>
        │             · 订单 → DISPUTED（自动流程暂停）
        ▼
双方陈述:  /escrow statement <订单号> <陈述>   （每方一条）
        │
        ▼
已读确认:  /escrow read <订单号>              （确认已读对方陈述）
        │
        ▼
举证:      /escrow evidence <订单号> <证据>    （举证窗口内，默认 24h）
        │
        ▼
裁决:      管理员 /admin/verdict 立案并形成结论
        │   · 结论=放款（RELEASE）或退款（REFUND）
        ▼
链上执行:  /admin/verdict/chain-execute（三方签名的裁决消息 → 合约执行）
        │   · 执行可以取消（chain-cancel）或重试（chain-retry）
        ▼
    终态（RELEASED 或 REFUNDED）

另外还有两条独立通道：
· 协商退款：任何时候一方 refund + 对方配合（不经过裁决）；
· 逃生票（合约内置，可以绕过任何运营方）：
    只在「合约升级提案冷静期且治理异常」时开放——双方各投一票 = 全额退回买方。
```

**争议相关的配置**：`TGG_DISPUTE_EVIDENCE_WINDOW`（举证窗口，默认 24h）、
`TGG_DISPUTE_REQUIRE_STATEMENTS`（是否强制先陈述再裁决）。

**裁决的三方签名**：裁决消息要被合约接受，需要 **联邦 + 买方 + 卖方**三方公钥对应的签名
（`TGG_VERDICT_BUYER_PUBLIC_KEY` / `TGG_VERDICT_SELLER_PUBLIC_KEY`）。不配置的话这条路
是关闭的——争议单就只能走协商或逃生票。

## 第 7 章 费用

- 费率有仨：`TGG_FEE_PLATFORM_RATE`（平台）、`TGG_FEE_ARBITRATION_RATE`（裁决）、
  `TGG_FEE_FEDERATION_SHARE`（联邦分成）。默认全是 0，也就是免费。
- **首单免费**：`TGG_FEE_FIRST_ORDER_FREE`（默认开）。注意一个细节：如果同时开了「链上扣费」
  （`TGG_CHAIN_FEE_ADDRESS`+`TGG_CHAIN_FEE_RATE_BPS`），首单免费在链上兑现不了——程序会自动按
  「不豁免」生效，并在启动日志里 WARN 说明（免得出现「账面记了豁免、链上实扣了」的对不上账）。
- **链上扣费（方案 B）**：把费率直接编进合约部署参数，按单在链上扣；不配置就链上不扣、只记账。
- **台账与结算**：`GET /admin/fee-ledger` 看记账明细；`POST /admin/fee-ledger/settle` 标记结算。

## 第 8 章 心跳与对账（资金安全网）

**怎么跑的**：heartbeat.sh（每 10 分钟）调 `POST /admin/reconcile`（批量）→ 遍历
「非终态 + 近 7 天终态」的链上订单，跟链上状态对比、该回填的回填；发现异常推给管理会话。

**对账就三种结论**：

| 结论 | 意思 | 你会收到什么 |
|---|---|---|
| 一致 | 链上链下对得上 | 没什么（回执里 `dangers:[]`） |
| 链上领先 | 链上已经推进了（比如已放款）、链下还没登记 | 自动回填 + 常规通知 |
| **DANGER** | 资金异常：①链下已终态但链上还拿着钱（滞留在合约）②链上链下资金方向相反 ③链下取消但链上已完成 | **管理会话主动告警**（要人工去核） |

**超时提醒巡检**（同一脚本的第二步）：对超期还没提醒的订单，给买方推「一键处理」深链——
只提醒，不动链上资金。

**需要手动的时候**：全量对账 `curl -u $U:$P -X POST .../admin/reconcile`；单笔对账带上
`{"orderId":N}`；配合 `GET /admin/dispute-case` 和链上浏览器交叉核对。

## 第 9 章 合约升级治理

**为什么有这套**：每单合约的地址不变，代码可以通过治理升级（修问题、加固），
配了 **72 小时冷静期** + **逃生票**双保险。

**流程**：

1. **提案**（ProposeUpgrade）：用治理钱包对目标合约发新代码哈希——提案上链，倒计时开始；
2. **72h 冷静期**：用户可以围观；期间治理方可以 `cancel` 撤回；**万一升级出问题，
   用户手里有逃生票**（双方投票 = 全额退款，保护资金安全）；
3. **应用**（ApplyUpgrade）：冷静期满后发应用消息，合约切换到新代码
   （地址、资金、状态全程保留）；
4. **查状态**：`GET /admin/upgrade/status`（带上合约地址）看当前提案哈希和倒计时。

**操作上的提醒**：提案/应用消息要用升级钱包签名发送（每笔附一点 TON 当手续费）。
脚本化工具和安全的注意事项（服务器零私钥、冷签名）看部署教程 10.4 节和第 12 章。

**给用户的一段话**：升级期间订单行为不变；对升级有疑虑的话，冷静期内留意公告，
极端情况下用逃生票（Mini App 里出现投票按钮时）。

## 第 10 章 常见问题

**Q1：钱在谁手里？** 在**每单独立的链上托管合约**里，不在平台服务器上。平台没有提款权；
放款、退款、裁决执行都有链上约束兜着（还有 72 小时冷静期和逃生票）。

**Q2：机器人跑路了怎么办？** 合约层面「平台也动不了你的钱」：资金只有四条出口——「买方放款」
「退款」「裁决执行」「逃生票」，每条都有签名或时间锁约束。

**Q3：换钱包了怎么办？** 合约锁的是下单时登记的那个钱包。旧钱包还能用的话：任一方去订单页
发起退款（托管中就能退），钱退回原买方钱包，然后换新钱包重新交易。**链上没有改绑机制**
（这是防劫持的设计）——私钥一定保管好。

**Q4：订单卡住不动了？** 用 `/escrow status` 看当前状态和可用动作；超时的环节系统会自动提醒；
资金异常（DANGER）有对账看着，会告警。

**Q5：怎么自己对账？** 全部资金动作都在链上，拿合约地址去 tonviewer/tonscan 能核对每一笔；
订单状态和链上一致（心跳对账一直在校准）。

**Q6：怎么改我的信用公开范围？** `/escrow publish --detail <维度>` 精确开放；
`/escrow unpublish` 一键全关。

**Q7：评价能改吗？** 每单每人一次，提交后不能改——这是信誉数据，改了就没意义了。

**Q8：管理面板在哪？** 没有网页管理面板。管理能力就是 `/admin/*` 那组接口（第 4 章），
配合脚本或自动化用；所有管理动作都要 Basic 认证。

**Q9：支持哪些币？** 由部署方配置（`TGG_ALLOWED_CURRENCIES`），常见是 TON 和 USDT（jetton）。

**Q10：升级/维护期间还能交易吗？** 管理方可以广播暂停（`/admin/pause`），恢复用 unpause。
暂停不影响已有订单的查询，也不影响已托管资金在链上的出口。
