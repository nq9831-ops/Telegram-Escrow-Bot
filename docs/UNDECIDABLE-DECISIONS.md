## A. 阻塞项（不解决，对应功能一行都写不了）

### A1. 子代理并行能力被账户余额卡死 ⚠️ 最高优先

**背景**：你授权「可以派多个子代理完成任务」。本轮派发 4 个并行 worker 落地功能集群，
**4/4 全部失败**，报错一致：

```
OpenAI API error (invalid_request_error): Insufficient Balance
提示：DeepSeek 账户余额不足，充值后重试：https://platform.deepseek.com/top_up
```

已核实：**零代码产出、无半成品残留**（逐个类名查过 `find`，工作区干净）。

**我的建议**：二选一——① 给 DeepSeek 账户充值；② 用 `/model` 把 worker 的默认
provider 切到一个有余额的供应商。

**不决定的后果**：74 项缺失功能只能串行手写，无法并行；这是当前推进速度的**唯一瓶颈**，
其余技术障碍我都已排除。

### A2. Telegram Bot Token

**背景**：命令层接线与 Bot 接入（`SpringLongPollingBot`）需要 BotFather 发的 token。
我不能替你申请，也不能把 token 写进仓库（`.gitignore` 已挡住 `.env` 等，但仍需一个
注入途径）。

**我的建议**：走环境变量 `TELEGRAM_BOT_TOKEN`，代码里 fail-fast（缺失即拒绝启动，
而不是带着空 token 起来后静默不响应）。我可以在你给 token 后把这条路径写完。

**不决定的后果**：系统**没有任何用户可见表面**——全部 33 个类都是纯逻辑库，
用户无法与之交互。这也是「用户级验收」至今只能到服务入口的原因。

### A3. 生产数据库与本地库的迁移校验和

**背景**：本轮把 `V1__init_escrow.sql` 改成可移植 DDL（原因见提交 `f8d7142`：
原 MySQL 内联 `KEY idx_...` 语法 H2 解析不了，测试根本跑不起来）。但本地 MySQL 的
`tgg_escrow` 库里 `flyway_schema_history` 记着旧 checksum `-951161179`，

若想彻底重来，重建 `tgg_escrow` 库——但那是破坏性操作，**我不擅自执行**。

**不决定的后果**：应用连不上本地 MySQL；测试用 H2 不受影响，所以测试全绿但启动会失败。

## B. 商业决策（我只能给建议，定了才好写代码）

### B1. 平台费与联邦费用比例（T29 / T30）

**背景**：原文档只写「平台费自动划转」「联邦管理员费用自动划转」，没给比例与分配规则。

**我的建议**：费率做成配置项（`escrow.fee.rate`、`federation.fee.rate`），默认 `0`——
默认值不替你定价格，但让"忘记配置"表现为"没收费"而非"收费错误"。

**不决定的后果**：T29/T30 的划转逻辑无参数可依，只能做成空壳。

**（2026-09-24 补，来自用户提交的 ENACT 材料）**：业界（ENACT 协议）采用「0% 协议费」模式，
与本条既有建议「默认 0」一致。补充两条运营侧事实供你决策：① 走 Telegram **Stars** 支付时平台 0% 佣金，
但 Stars 兑换有汇率损耗（用户付 $2.40、开发者约收 $1.30）——**待核实**；② 走 **TON 直接收费**无此损耗。
若选 0%，成本可由增值服务（群内置顶）、向商家收费、捐赠等覆盖。整理见 `docs/requirements/04-x402与ENACT.md`。

### B2. 首单保障的规则（T44）

**背景**：「首单保障」在原文档里只有名字。保障什么（免手续费？先行赔付？保额上限？）、
如何判定"首单"（按用户？按设备？）、赔付资金从哪来，全都没写。

**我的建议**：先做**免首单手续费**这一最简形态（判定按用户 ID 首笔成功交易），
其余形态（先行赔付）需要资金池设计，风险高，建议后置。

**不决定的后果**：T44 只能留空壳。

### B3. 信用分模型（T3 / T47 / T53）

**背景**：「信用分联动」「交易信用可视化」「互刷不累加信用」都要信用分，
但**分怎么算**（维度、权重、衰减、初始分）一个字都没有。

**我的建议**：先定一个最小可用模型——初始 0 分、每笔成功交易 +N、争议败诉 −M、
按时间衰减；全部参数配置化。等有真实数据再调权重。

**不决定的后果**：T3/T47/T53 全部无法实现；且「互刷不累加」（T53）缺少判定依据。

### B4. KYC 最小化的口径（T22）

**背景**：原文档说「KYC 最小化 + 加密」，但"最小"到什么程度（只手机号？实名？证件？）
是合规问题。

**我的建议**：**这条我不给具体建议**——它取决于运营方所在法域的牌照要求
（菲律宾 BSP 的 VASP 新牌照目前处于**无限期冻结**，见 `private/OPERATOR-COMPLIANCE-GUIDE.md`）。
在牌照路径没定之前写 KYC 是白写。

**不决定的后果**：T22 无法实现；更根本地——**能不能合法上线尚未确定**。

### B5. 许可协议

**背景**：当前按 AGPL 3.0 处理（`LICENSE` 是 AGPL 全文）。但原文档未明确指定协议。

**我的建议**：若希望衍生作品也开源，AGPL 3.0 合适；若希望商业友好，
Apache-2.0 / MIT 更合适。**这影响别人能否拿你的代码去运营**。

**不决定的后果**：按现状（AGPL）继续，但可能与你的分发意图不符。

## C. 技术方向取舍（我已选了默认值，你可推翻）

### C1. TON 合约的多签语义

**背景**：多签仲裁（T15）说「2/3，必须含联邦节点」且「买方 + 卖方联合签名无效」。
这条规则的实际后果值得你知道：

- 三方是 `买方 / 卖方 / 联邦`，有效组合只剩 `{联邦+买方}`、`{联邦+卖方}`、`{三方}`。
- **「买方+卖方无效」意味着联邦是唯一必备签名方**——争议中双方对立，
  联邦选边即定胜负。所以这个「2/3 多签」**不提供对联邦的制衡**，本质是联邦一人裁决。

**我的默认选择**：按原文档实现（必含联邦）。

**替代方案**：允许 `{买方+卖方}`（双方和解），可保住"双方一致时不必经第三方"；
但会让双方串通绕开担保。详见 `private/state-machine.md` §8.4 的论证（该建议已被推翻，
理由是"担保"语义下串通即失效）。

**不决定的后果**：按默认继续。但你应当知道"多签"这三个字在这里的实际含义。

### C2. 合约可升级性（T43）与资金隔离的冲突

**背景**：T43「代理合约可升级」与 8.2「每笔交易独立地址，资金隔离」方向相反——
可升级意味着能事后改资金规则（监管穿透下视为实质控制），独立部署则升级无从谈起。

**我的默认选择**：**默认不启用可升级**（`escrow.contract.upgradeable=false`）。
理由是原文档反复强调「资金安全变态级」「合约中无开发者提款函数」，
与可升级方向矛盾；保守取向应是不可升级。

**不决定的后果**：按默认（不可升级）实现。若你要可升级，需同时定升级权限归谁、
时间锁多久、以及如何向用户披露。

### C3. T22「KYC 最小化」与「不存聊天记录」的冲突

**背景**：原文档同时要求 KYC（需留存身份数据）与「不存聊天记录」（隐私设计）。
这两者与 AML 的「记录保存 5 年」义务三方冲突。

**我的默认选择**：**不做任何身份数据采集**，把 KYC 留空壳 + 显式开关（默认关闭）。
理由：采集了就得合规保存，在牌照路径未定前是纯负债。

**不决定的后果**：按默认（不采集）实现。

## F. TON Connect 钱包取向（新增，2026-09-24）

**背景**：你提供了 Telegram 官方钱包对 TON Connect 的支持说明（整理见 `docs/requirements/02-TON-Connect.md`）。
官方钱包是**托管钱包**（custodial，密钥由 Telegram 服务器保管），而本项目 V2.0 核心原则写「签名在用户设备」
「服务器不碰私钥」——两者不冲突，但**语义从「非托管自持」滑向「托管」**。

**我的建议**：
- 钱包列表**两者都列**（Telegram 官方钱包 + Tonkeeper 等非托管），默认优先展示官方钱包以保证体验；
- **据实修订安全叙事**：若采用托管钱包，README/术语里「签名在用户设备」应改为「签名经钱包完成」——
  这属合规风险（承诺与实现不符），不只是文案；
- 多签拼接（T15/T16 的联邦签名 + 托管钱包签名）需在 S5 合约设计时一并确定。

**不决定的后果**：T7/T8/T9/T10/T11 与 S5 的钱包集成方向未定；安全文档口径可能与实现不符。

## G. TON Pay 集成的前置（新增，2026-09-24）

**背景**：你提交了 TON Pay 方案（整理与独立核实见 `docs/requirements/03-TON-Pay与Tolk.md`）。
TON Pay 是 TON 基金会 2026-02 的支付层 SDK，可用于「买方锁资」这一步。但有两项前置不属技术侧自行决定：

1. **Merchant API Key**（凭据）：无 Key 则拿不到 webhook 通知与 Dashboard，只能手动轮询链上。
   需你申请。它是**必须安全保管的服务端密钥**（`TONPAY_API_SECRET`），走环境变量注入、禁入库。
2. **Web/HTTP 端点缺口**：webhook 需要一个对外 HTTP 端点，而项目**当前没有 Web 层**
   （无 Spring Web 依赖、无 `@RestController`）。这是独立的基础设施项，需先决定是否引入 Web 服务及其安全边界。

**我的建议**：把「引入 Web 层」作为 S5 的前置**显式立项**（而非顺手加）；先申请 API Key；
在 S5 合约设计里一并确定「每笔交易独立地址」与 TON Pay `recipientAddr` 的关系。

**不决定的后果**：T9/T10/T11 的支付路径无法开工；webhook 验证没有落点。

## H. 安全设计约束（新增，2026-09-24）

**背景**：你提交的 Fragment API 与 Permit Signature 防御材料
（整理见 `docs/requirements/05-Fragment与Permit钓鱼防御.md`）带出三条**设计级约束**，
需在 S5 合约与 T8–T11 前端设计时落实，而非事后补：

1. **不采用要求交出钱包助记词的第三方 SDK**：市面"无需 API Key"的 Fragment SDK 普遍要求
   `TON wallet seed phrase (12/18/24 words)`（核实依据见 05 号文档）——与「服务器不碰私钥」直接冲突。
   若需 Stars 能力，走 Telegram 官方 Bot API 的 Stars 支付（生态内原生、不涉助记词）。
2. **本项目自身不得制造"无限授权"面**：Permit 钓鱼（SPF 2026-07 警示）之所以能成，是因存在
   "预先授权、后续免批准"原语。合约应**不提供**无限额度/长期授权接口；任何 approve 类操作
   默认最小额度、默认不启用，且必须让用户看到额度与用途。
3. **签名前展示人类可读的交易摘要**：作为 T8/T9/T10/T11 的统一交互要求（无论钱包是否托管）。

**不决定的后果**：沿用非官方 SDK 或引入无限授权，等于自己制造被钓鱼的攻击面。
