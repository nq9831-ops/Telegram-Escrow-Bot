> 以下各条是**合约侧接口**与**链上部署参数**的决策，此前只散落在 `.rivet/HANDOFF.md`，现归并到本清单。
> （原写"这五条"，但 A0-6 许可、A0-7 信任锚点陆续加入——**不再写死条数**，以免每次都失修。）
> 每条标了**依据**与**核实状态**——未核实的明确标出，不当作结论。

### A0-1. Jetton 可信钱包地址来源（ET-50）——建议：**链上派生，不配字面地址**

**背景**：合约要校验入金来自可信 jetton 钱包，但"可信钱包地址从哪来"没有定。
**建议**：部署时只存 **jetton master 地址**（或 wallet code），合约内用
`AutoDeployAddress{workchain, stateInit}.calculateAddress()` 算出预期钱包地址，再与 `in.senderAddress` 比对。
**依据（已核实）**：本地 stdlib `.acton/tolk-stdlib/common.tolk:1648` 的示例正是
`val jwAddress = jwDeployed.calculateAddress();`，且 `addressMatches` 已被标 `@deprecated`
（"Use `a == jwDeployed.calculateAddress()` instead"）——这就是官方当前推荐的写法。
**代价**：需要 master 的 wallet code（部署时从链上读一次写入存储，或存 code hash）。
**不决定的后果**：`FundMessage` 只能接受任意来源的 Jetton 转账 = 假 Jetton 可入金。

> **✅ 落地情况（2026-09-25；经提交后审查纠正）**：实现取 **SPEC 的口径**——部署时
> **预计算并写入「我方（本合约自己的）jetton 钱包」地址**，链上只做等值比对；**不做**链上派生。
> - **关键语义（TEP-74 原文第 82/95 行，已核实）**：`transfer_notification` 由**收款方自己的
>   jetton 钱包**发出，报文里的 `sender` 是**上一持有人（买方）**——**两个地址不同、两处都要验**：
>   ① 实际发送者 == 我方钱包（否则 `NotTrustedWallet`）；② 报文 `sender` == buyer（否则 `NotBuyer`）。
> - ⚠️ **首版实现把可信锚点误设在「买方钱包」上**（且只验实际发送者、不验报文 sender），
>   真实通知会被全量拒、第三方转入即可锁定 —— 该缺陷由**提交后审查**发现，已修正并补测试。
> - **为何不链上派生**：`calculateAddress()` 需要该 master 的 jetton **wallet code**（cell），
>   而存储已接近单 cell 1023 bit 上限（故新字段走 `Cell<EscrowExtra>` 引用）；派生属可后置的优化。
> - **当前状态（已随增量 5 更新）**：jetton **入金与出账均已实现**——入金认我方钱包的
>   `transfer_notification`，出账向我方钱包发标准 `transfer`（0xf8a7ea5），报文指定收款方；
>   有测试断言出站消息的 dest 与 body。**入金须附 ≥0.05 TON 作燃料**（`InsufficientFeeTon`）。
>   出账随附 TON 为**固定占位值**（费率/存储费池未定案，见 A0-3）。**链上未部署、未真机验证。**
>   ⚠️ **措辞边界（提交后审查纠正；2026-09-29 复核更新）**：该拒绝**只中止通知交易**，**不能**阻止
>   jetton 早已记入我方钱包——"拒绝"不等于"资金没进来"。**但该边界写成时合约尚无划出能力，
>   增量 5 之后出账已实现**，故"资金只能进不能出"已不成立；当前真实缺口是
>   **链上未部署 + 未真机验证 + 出账随附 TON 为占位值（见 A0-3）**，而不是"缺出账"。

### A0-2. 仲裁消息的签名字段布局（被 C1 挡）——建议：**链下裁决 + 链上单签执行**

**背景**：`ResolveMessage` 要承载"2/3 多签且必含联邦"，但**链上验签还是链下裁决**未定。
**建议**：链下裁决、链上只接受**联邦的单签裁决消息**；不做链上多签验签。
**依据**：语义已在 `docs/requirements/SPEC.md:213`（ET-15：2/3 必含联邦）与 `:325`
（平台费 ≠ 仲裁费、费率默认 0%。**已核实**）。链上验 2/3 要么引入官方 multisig 钱包合约
（多一套地址与交互面），要么自实现 ed25519 验签（消息体与 Gas 都贵）；
而"必含联邦"本质是**链下治理约定**，链上只需保证"只有联邦能改状态"。
**未核实**：官方是否有现成的链上多签模板可直接复用（web 搜索本轮超时，未取得来源）。

### A0-3. 存储费池额度——建议：**先不加机制**

**背景**：SPEC 提到 fund 时预留 `storageFund`，但额度与实现形态未定。
**建议**：维持现状"合约留存余额自付"；等有真实 Gas 数据再定额度
（基线已生成：`gas-baseline.json`）。
**注意**：若将来要加 `storageFund` 字段，会撞单 cell **1023 bit 上限**（编译器实测 1169–1409），
**必须同时**改成 `extra: Cell<EscrowExtra>` 引用结构；`@overflow1023_policy("suppress")` 是把失败
推到运行时，不可取。

### A0-4. 维护期超时的链上表达——建议：**不写链上自动超时**

**背景**：维护期到点后应能自动确认/退款，但 TON 没有链上定时器。
**建议**：`maintenanceDeadline` 只作**记账**；到点判定由 Java 侧既有的惰性判定
（`TradeTimeoutPolicy`，下次交互时结算）完成。与项目"不引入调度器"的非目标一致。

### A0-5. Java ↔ 合约接口——建议：**引入官方维护的 TON Java SDK 收口**

### A0-7. 部署参数：`TGG_CHAIN_JETTON_MASTER` 与网络（信任锚点）——建议：**先测试网自建 jetton，主网 USDT 留到部署时**（2026-09-29 联网 + 链上核实）

**背景**：`/admin/chain/own-jetton-wallet` 现返 503（未配置 `tgg.chain.jetton-master`），即链上能力关闭——
这是 fail-closed 的默认，不是缺陷。该值与网络一旦配上，就会被用来推导 `ownJettonWallet` 并（部署时）
写入合约 storage（见 A0-1）；**写错不会报错，只会静默收不到入金**。

**建议**（分两阶段，与本项目「不做合约主网部署、不动真金」的非目标一致）：

1. **现在走测试网**：`TGG_CHAIN_TESTNET=true` + `TGG_CHAIN_JETTON_MASTER=<自建的一枚测试网 jetton master>`。
   自建而非找现成件，是因为供应量/精度/管理员都在你手里，可反复演练入金 → 出账 → 回弹。
   本仓已有 Acton（`~/.acton/bin/acton`，v1.2.0），官方路径为
   `acton new my-jetton --template jetton`（生成 `contracts/JettonMinter.tolk` + `JettonWallet.tolk` + `scripts/`）
   → `.env` 填 `JETTON_DECIMALS` / `JETTON_ADMIN_ADDRESS` → `acton build && acton test`
   → `acton wallet new --name deployer --version v5r1 --local --secure=true` 再 `acton wallet airdrop deployer --net testnet`（水龙头）
   → `acton run deploy-testnet`（**摘自 docs.ton.org「How to create a jetton with Acton」**，非推测）。
2. **主网（时机未到）**：`TGG_CHAIN_TESTNET=false` + **USDT₮ 的 jetton master
   `EQCxE6mUtQJKFnGfaROTKOt1lZbDiiX1kCixRv7Nw2Id_sDs`（decimals=6）**。
   **三重独立核实**：① 官方文档 `ton-blockchain.github.io`（Jettons payments processing）与 `docs.ton.org` 均
   明写该地址即 TON 上 USDT 的 minter；② toncenter v3 API 实测返回 `decimals="6"`、
   `uri=https://tether.to/usdt-ton.json`、`total_supply=1429976002510000`（按 6 位＝**14.30 亿**，
   与浏览器所示 Max supply 1.43B 吻合）；③ 本仓 `AdnlJettonWalletQuery` 的实测路径对该地址
   返回 `exitCode=0` 并解析出 `EQDmVdCZ2SALvyfCDVlPLr0hoPhUxgjNFtTAxemz9V_C5wbN`。
   ⚠️ 官方文档对主网的原话是 "Funds at risk … Successful mainnet transactions cannot be rolled back"，
   并要求先在 emulator 与 testnet 跑通——**与本项目非目标一致**。

**配之前必须三处对齐**（错一处即静默失效）：`TGG_CHAIN_TESTNET` ↔ jetton master 所在网络 ↔
合约部署所在网络。三者不一致时推导出的 `ownJettonWallet` 是**另一个网络的地址**，而它会被写进
storage 当信任根。

**配好后的验证**（改 env + 重启后即可验，不必等合约部署）：
`curl -u <admin> 'http://127.0.0.1:8080/admin/chain/own-jetton-wallet?contract=<任意合法地址>'`
→ 期望 **200 + ownJettonWallet**；**502** 才是"节点不可达"（换 provider 的信号）；**503** 说明 master 没配上。

**决策状态（2026-09-29 · 两项均已拍板）**：

> - ✅ **计价资产：USDT 作为唯一计价资产**（用户拍板）。**落地方式取 (b) 配置式，已实现**：
>   新增 `AllowedCurrencies`（`tgg-escrow`），两个创建入口（`EscrowTradeService.initiate` /
>   `TradeInviteService.create`）各加一道 `requireAllowed(...)`（构造器注入，缺参即抛，无"忘传=全放行"的默认）。
>   配置键 **`TGG_ALLOWED_CURRENCIES`**（`tgg.allowed-currencies`，逗号分隔）：
>   **留空 = 不收窄**（TON + USDT，行为与从前一致）；写 `USDT` 即只收 USDT；
>   写成 `BTC` 之类在**启动期**直接抛（fail-fast，不静默丢弃）。`TradeCurrency` 枚举**未动**。
>   ⚠️ **默认是不收窄**，故线上要真正只收 USDT，**必须显式配这一项**（在 `/www/wwwroot/tgg/env.sh` 加 `TGG_ALLOWED_CURRENCIES=USDT`）。
> - ✅ **走 testnet**（用户拍板）——上面那条主网 USDT₮ 地址保留为「时机到了再用」的值。
> - ✅ **testnet 演练已执行（2026-09-29）**：自建 jetton 部署成功（master `kQC87Ycbr28MRbK7PufCcsV_nHR6QUra1a_lsn05_UG9P_BV`）、`own-jetton-wallet` 返 **200**——完整实录与一处**网络 tag 待跟进观察**见文末「A0-7 演练实录」。
>
> **当时为什么没选收窄枚举（留作取舍记录）**：币种受理由 `TradeCurrency` 枚举**硬编码**
> （仅 `TON` / `USDT`，`application.yml` 里**没有**任何币种配置项），校验点 `requireSupported(...)`
> 落在 `TradeInitiationRequest:38` 与 `TradeInvite:135` 两处，且 `TradeCurrencyTest:60/67` **断言 TON 可受理**。
> 因此有两种落法：
> **(a) 收窄枚举**（删 `TON`）——会直接打断 TON 路径并让既有断言失红，且合约的 `asset=0`（TON）分支沦为死码；
> **(b) 配置式**——枚举保留"能不能"，另加部署侧「允许集」配置（默认两者，部署设 USDT-only），校验点读配置。
>
> **(b) 之所以胜出**：它正是本项目自己的原则「**代码回答能不能，配置回答允许什么**」；而收窄枚举把
> **部署选择**写成了**能力事实**，将来想恢复 TON 只能改代码重发版。

### C1. TON 合约的多签语义

**背景**：多签仲裁（T15）说「2/3，必须含联邦节点」且「买方 + 卖方联合签名无效」。

## L. 哈希脱敏与部署陷阱（新增，2026-09-24）

**背景**：你提交的风险提示（整理与核验见 `docs/requirements/09-风险提示.md`）带出两条**落到实处**的问题：

1. **`LogSanitizer.maskUserId` 无盐且仅 24 bit**（已读源码确认：`SHA-256(userId)` 取前 6 位 hex）。
   后果：可被**预计算/字典反推**（攻击者列候选 ID 逐个哈希比对），且大用户量下会**碰撞**。
   建议 **加部署级盐值（配置项，走环境变量）+ 加长输出**。**链上 proofHash 同理必须加盐**——
   否则"交付凭证"若是常见短语即可被反推。
2. **Telegram 隐私模式**：Bot 默认只能看到命令与 @提及；要看到群内全部消息，须在 BotFather
   **关闭隐私模式 → 移除 Bot → 重新添加**。本项目的「群聊留痕」（T33/T37）**完全依赖此**——
   漏配会让留痕**静默失效**（Bot 不报错，只是看不到）。建议：写进部署文档 + Bot 启动**自检告警**。

**另发现**：`09` 的"Gas 费谁出"与 `04`（storageFund）、`08`（仲裁费）是**同一件事**——
建议**归并为「费用与 Gas 承担」单一设计项**，避免分散在多处各自表述。

**不决定的后果**：脱敏可被反推（隐私泄露）；部署漏配即核心功能静默失效。

## M. 是否引入 Agentic Wallets（免逐笔授权）（新增，2026-09-24）

**背景**：TON Tech 2026-04 推出 Agentic Wallets（开源、**自托管**、可撤销、有硬性限额），
允许 AI 代理在用户资助的钱包内**免逐笔授权**自主交易。核验属实（见 `docs/requirements/11-生态对齐.md` 第三节）。

**为什么这是方向性决定**：项目核心原则含「**签名在用户设备**」，现有流程是**用户逐笔确认**
（含已落地的 `TradeCommandHandler`）。采纳 Agentic Wallets 意味着**改变"谁在什么条件下动用户的钱"**——
**不是加功能，是改信任模型**。

**若采纳，必须同时满足**：
- 向用户明确披露「**代理权限一旦授予，限额内的操作不可撤回**」；
- 与 `05`（Permit 钓鱼防御）、**H 节**（不制造无限授权面）**一并评估**提示注入风险面；
- 明确与 T15/T16 多签仲裁的拼接方式（S5 设计时定）。

**我的建议**：**暂不引入**（项目尚未上线、逐笔确认的摩擦可接受）；若未来面向高频小额场景再议。

**不决定的后果**：若默默引入，等于在"用户逐笔签名"的承诺下开了免授权通道——安全叙事与实现不符。
