## 必须先定死的五个口径（本波最容易出错处；写进代码注释＝代码即规格）

1. **`completed`** = 终态 `RELEASED` 的笔数。**不含** `REFUNDED` / `CANCELLED`——退款的交易不是「完成」。
2. **`disputeRate`** = `DISPUTED` 笔数 ÷ 参与总笔数（含终态）。分母写进注释，避免日后两种口径并存。
3. **`positiveRate`** = `score ≥ 4` 的评价数 ÷ 评价总数；**无评价 → 0**。理由：`TraderTier` 里 `<5` 笔一律 `NEWBIE`，故 0 分**不会惩罚新人**（新人本就不参与评级）；且「没被好评就不加分」比「未知即满分」更保守。
4. **`activeDays`** = 首笔 `created_at` 至末笔 `updated_at` 的**自然日跨度（含两端）**。理由：与 `CreditScore` 的权重注释用词「活跃时长」一致；且只需一条与既有 `findMaxUpdatedAt…` 同形的聚合，不必引 `count(distinct date(...))`。
5. **`diversityShare`** = `CounterpartyDiversityScorer.maxShare(对手→笔数)`；对手分布来自一条 **GROUP BY 对手** 的新查询（**新查询，不是新表**）。对手定义为订单的另一侧（买方视角取卖方、反之亦然）。

**Wave 3 与原计划的偏差与增补（4 处）**：

1. **带他人 ID 时明确拒绝**（原计划只写"只查自己"，未定义带参行为）。理由：榜单已强制匿名，
   若这里忽略参数回自己的，会让人误以为看到的是所填 ID 的信用——**比拒绝更糟**。
2. **新增 `CreditBreakdown` + `CreditSummaryView` 两个类**（原计划只说"渲染"，未指定落点）。
   动机是**口径单点**：五维比率的算法留在 `TraderCreditService`，渲染层只吃算好的值，
   避免"文案解释一套口径、分数来自另一套"。`scoreOf` 改为经 `breakdownOf` 派生，
   并用一条用例钉住"拆解值喂回 `CreditScore` == `scoreOf`"。
3. **量表满分线提为公开常量**（`CreditScore.COMPLETED_FULL` / `ACTIVE_DAYS_FULL`）——
   否则渲染层会各写一份 50 / 365，日后改量表即静默漂移。
4. **零历史用户追加"来源解释"**（原计划只要求"如实标注暂无评价"）：零历史也有 40 分
   （两个反向维度在零数据时给满分），故文案必须点明这 40 分**来自哪两个维度**。
