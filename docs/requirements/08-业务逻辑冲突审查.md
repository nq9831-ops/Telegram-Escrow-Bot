## 三、整理观察（补充，非原文）

### 3.1 报告 1.4 的"死锁"在项目里不成立——但报告的提醒有价值
核验显示 `TradeTimeoutPolicy` 对未登记状态返回不动作，`DISPUTED` 不在规则表里，
所以"争议 + 超时"不会同时触发。**报告担心的死锁在当前代码结构下不会发生**。
但报告的建议（**明确状态优先级：争议 > 维护期 > 超时**）应当写成**显式不变量**并加测试钉住——
否则将来有人"顺手"把 DISPUTED 加进超时规则表就会引入该冲突。建议：在 `TradeTimeoutPolicy` 加一条测试，
断言「DISPUTED 状态永不超时」。

### 3.2 报告 1.1 的措辞与文档原文不符，但矛盾是真的
文档没有"从败诉方**保证金**扣除"这句话；实际是「**押金**由不服方承担」（`01` L200）与核心规则
「免保证金」（`01` L189）相抵触。**结论方向一致，但引用必须用原文措辞**——
否则按报告去改文档会"改一个不存在的句子"。建议：统一术语（押金 / 保证金 / 仲裁费三者分清），
再决定免收哪一个。

### 3.3 报告的 1.2 / 1.3 直接改变已批准计划的 Wave 1b 设计
Wave 1b 原计划实现 `TradeGroupLifecycle`（交易群五态）与 `VoterRecusal`（回避窗口）。
报告的两条方案会**改变它们的规格**：
- `TradeGroupLifecycle`：**群与交易 ID 绑定**、每笔新交易新建群、不复用（原计划未含此约束）；
- `VoterRecusal` / 投票资格：**投票人分层（权重 3/2/1）+ 观察员角色**（原计划只有"排除近期交易者"）。
→ 这两条是**对已批准计划的偏离**，需记录并按新规格修订（尚未开工，改动成本为零）。

### 3.4 1.6 的方案带来一条**用户预期**上的新风险
报告建议「平台费可 0%，但**仲裁费始终存在**（从败诉方押金扣除）」。
问题在文案层：用户看到「0% 平台费」会理解为"不花钱"，但败诉仍需付仲裁费——
**若不在文案里说清"平台费≠仲裁费"，这是误导**（与 `07` 里 V3.0 把「0%协议费」列为核心规则相呼应）。
建议：对外统一表述为「平台费 0%，仲裁费仅在败诉时产生」。

### 3.5 1.3 的"权重 3/2/1"是新的业务参数
分层权重（核心/资深/普通 = 3/2/1）与观察员门槛（≥1 笔）**都是业务决策**，
不是技术默认值，建议并入待决清单 B 组（信用分/投票资格同源）。
