# TON Connect 与 Telegram 官方钱包（整理）

> 来源：用户提供的说明（Telegram 官方钱包对 TON Connect 的支持）。
> 本文是整理 + 对本项目的影响分析；「张力分析」与「决策点」为整理者补充，非原文。

## 1. 要点（原文整理）

### 1.1 官方钱包原生支持 TON Connect
Telegram 官方钱包（Wallet in Telegram）本身是基于 TON 的钱包，**默认支持 TON Connect 协议**——
该协议是 Telegram 生态内钱包与应用的标准通信协议，官方钱包已原生集成。在 TON Connect 的官方
钱包列表中，`telegram-wallet` 被列为支持的钱包之一，Universal URL 格式为
`https://t.me/wallet/start?startapp=`。

### 1.2 用户绑定流程
用户通过 TON Connect 连接应用时，会看到「Open Wallet in Telegram」提示，点击后**直接唤起 Telegram
内置钱包**完成连接——用户不需要离开 Telegram，也不需要额外下载 Tonkeeper 等外部钱包。
若用户还没有 DeFi Account，可在连接过程中直接创建，系统会引导保存 24 词助记词。

### 1.3 连接后的管理
用户可在 DeFi Account 的「Connected Apps」中查看和管理所有已连接应用，支持单独断开或
「Disconnect All Apps」。

### 1.4 对本项目的意义（原文观点）
担保交易平台需要用户签名确认交易。通过 TON Connect 绑定 Telegram 官方钱包，用户可在 Telegram
内部完成所有签名操作、不跳转外部应用——与本项目「用户只面对一个 Bot」的设计原则一致。

### 1.5 技术实现要点（原文）
Web 平台集成 TON Connect 时，在钱包列表中**优先展示 Telegram 官方钱包**。TON Connect 是标准协议，
官方钱包作为 TON 生态默认钱包，连接体验比外部钱包更流畅（一键唤起、无需额外确认）。

### 1.6 关键提醒（原文）
**Telegram 官方钱包是托管钱包（custodial），密钥由 Telegram 服务器保管**——与 Tonkeeper 等
非托管钱包不同。对担保交易场景，托管钱包的便利性（无需管理助记词、恢复简单）可能更适合普通用户。

## 2. 与本项目核心原则的张力分析

本项目 V2.0 核心原则写着「**签名在用户设备**」「**服务器不碰私钥**」。引入托管钱包后，这两条的
实际含义需要重新校准：

| 项目原则（原文） | 官方钱包（托管）实况 | 判定 |
|---|---|---|
| 服务器不碰私钥 | 密钥由 **Telegram** 保管，**我们的服务器**确实不碰 | ✅ 仍成立（但要区分「我们的服务器」与「Telegram 的服务器」） |
| 签名在用户设备 | 签名发生在 **Telegram 服务器**（用户授权触发），不在用户设备 | ⚠️ **口径变化**——不再是「用户自持密钥、设备本地签名」 |
| 资金安全「变态级」 | 引入对 Telegram 托管的信任；用户失去密钥自持 | ⚠️ 需重新表述安全承诺 |
| 用户只面对一个 Bot | Telegram 内一键唤起、无需外部钱包 | ✅ 契合 |
| 免管理助记词/恢复简单 | 托管钱包天然具备 | ✅ 契合（用户体验） |

**结论**：不冲突，但**语义从「非托管自持」滑向「托管」**。这不是技术缺陷，是产品取向——
原文档的「签名在用户设备」偏向非托管安全叙事，而官方钱包走的是托管便利路线。两者不能同时
对用户宣称。

## 3. 决策点（建议记入 `docs/UNDECIDABLE-DECISIONS.md`）

1. **默认钱包取向**：Telegram 官方钱包（托管、便利）作为默认？还是 Tonkeeper/TON Space
   （非托管、自持）？还是**两者都列、让用户选**？
2. **安全叙事口径**：若采用托管钱包，README/术语中「签名在用户设备」「服务器不碰私钥」等
   表述需据实修订，避免承诺与实现不符（这是合规风险，不只是文案）。
3. **多方签名架构的连带影响**：托管钱包下，"用户签名"由 Telegram 代理完成——这与本项目
   T15/T16 的多签仲裁（联邦节点签名）如何拼接，需在 S5 合约设计时一并确定。
4. **助记词引导**：原文提到「引导保存 24 词助记词」——托管钱包理论上不需用户保存助记词，
   此处（存疑），需核对 Telegram 官方钱包的实际流程。

## 4. 影响的功能项

| 编号 | 功能 | 受影响方式 |
|---|---|---|
| T7 | Web 交易界面 | 需集成 TON Connect UI，钱包列表排序（官方钱包置顶） |
| T8 | Telegram OAuth 登录 | 与 TON Connect 的用户身份打通 |
| T9 | TON USDT 支付 | 签名路径经官方钱包 |
| T10 / T11 | 合约托管 / 资金冻结释放退款 | 托管钱包下的签名与多签拼接（见决策点 3） |
| S5 | TON 托管合约 | 多签语义（C1）与之耦合 |

## 5. 与既有待决事项的关系

- **C1（多签语义）**：原 `UNDECIDABLE-DECISIONS.md` C1 已指出「必含联邦」实为联邦一人裁决。
  托管钱包引入后，"用户签名"的可验证性进一步下降（由第三方代签），C1 的取舍需复核。
- **D（TON 确认数语义）**：托管钱包下的交易确认路径可能与自持不同，S4 链上源实现前需核实。
