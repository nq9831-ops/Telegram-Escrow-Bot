## 三、整理观察（补充，非原文）

### 3.1 ⚠️ 第 1 条（原地编辑）引入一个**持久化需求**——不只是 UI
要"同一笔交易的后续操作编辑原消息"，必须保存 `(orderId → chatId, messageId)` 的映射。
项目当前持久化**只有 `escrow_orders` 表**（+ `EscrowOrderRepository`/端口实现），**没有这个映射**。
→ 需 **V2 Flyway 迁移 + 新的存储端口**。同理第 4 条（通知模式）需**用户偏好存储**（新表或字段）。
**所以这两条不是"纯 UI 细节"，而是带持久化的结构性新增**，应并入 S1 规格与迁移计划。

### 3.2 必须区分「静默」与「临时」——两者不同
- **静默**（`disable_notification`）：消息**照常出现在聊天里**，只是不响铃/不震动 → **不破坏证据保全**；
- **临时**（Ephemeral Messages，见 `07`/`09`）：**仅单个成员可见** → 用于隐私通知，**不能**用于需留痕的关键节点。
`08` 的 2.4 已定"关键节点用永久消息、倒计时用临时"；本次的"静默"是第三个维度。
**建议在 S1 规格里把三个维度写清**（可见范围 / 推送与否 / 留存与否），否则实现时极易混淆。

### 3.3 第 3 条若采纳，会**改动已落地的类**
项目已有 `TradeStatusView`（T2，生成"摘要 + 下一步"文案）。本条的格式标准
（短标题 + emoji + 列表）会成为**该类的输出规范**——即**已落地的 `TradeStatusView` 会受影响**（改 summary/nextStep 呈现）。
这不是"新增"，是**修订既有输出**，需在批准后单独作为一个逻辑单元做（含测试更新）。
