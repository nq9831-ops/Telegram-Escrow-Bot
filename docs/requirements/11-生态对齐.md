## 一、八条要点

1. **Agentic Wallets**（TON Tech，2026-04）：AI 代理在用户资助的钱包内**免逐笔授权**自主交易；
   用户保留主密钥，代理获合约级窄权限（预算内转账/兑换/DeFi），可随时撤销。
2. **Guardian 机器人**（Telegram，2026-06，材料称）：官方"AI 管理员"概念——处理入群申请、
   跑 Mini App 筛选（问答/测验/政策检查）、入群后继续执行主题规则。
3. **Gram 钱包**：Telegram 官方钱包更名，**自托管**默认钱包（支付/转账/购买）；
   原「Wallet in Telegram」更名 **Walt**（更广加密平台，300+ 资产、永续合约等）。
4. **交付证明的链上验证状态**：信用可视化不仅展示"完成笔数"，还展示"交付证明的链上验证状态"。
5. **ENACT 的 Auto-Claim**：评估者失联时，提交者可自动认领资金，避免无限期拖延。
6. **4LNQ 的二维码交付确认**（P2P 包裹配送）：发送方生成 QR → 接收方展示 → 承运方扫描 → 合约释放资金。
7. **Rich Messages**（Bot API 10.2，2026-07）：21 种富块（标题/列表/表格/媒体），可作结构化展示。
8. **投票时间戳**（Telegram，2026-03，材料称）：Voting Timestamps；结合投票截止时间显示。

## 二、⚠️ 核验纠正：`02` 的"官方钱包是托管钱包"**已不成立**

`02-TON-Connect.md` 此前依据用户材料写下「**Telegram 官方钱包是托管钱包（custodial），密钥由 Telegram 服务器保管**」，
并据此在待决 **F 节**建立了"托管 vs 自持"的张力分析。

**本次独立核实（多条来源）推翻该前提**：
- Telegram 已推出**自托管（self-custodial）Gram 钱包**，并将其设为**默认**选项；
- 原「Wallet in Telegram」**更名为 Walt**（定位更广平台：交易/投资/收益/衍生品）；
- Durov 原话大意：计划把 **native non-custodial** 钱包带到每个 Telegram app；
- 改名动因之一是 **MiCA 合规**（把钱包/社交面与交易中心分开）。

**影响**：
- F 节「托管 vs 自持」的**张力前提不再成立**——采用 **Gram 钱包符合**项目「服务器不碰私钥」「签名在用户设备」的原则；
- 但 **Walt**（交易/衍生品平台）**可能仍是托管性质**，若把它作为"高级选项"则张力转移到 Walt 一侧；
- `02` 文档需按此更正，且"官方钱包"一词现在**指代不明**（Gram 还是 Walt？）——引用时必须点名。

## 三、Agentic Wallets：与项目原则的**方向性冲突**（需决策）

核验：**真实**（TON Tech 2026-04-28，开源、**自托管**、可撤销、有硬性支出限额；用户资助并保留所有权）。

但引入它对本项目是一个**方向性取舍**：
- 项目 V3.0 核心原则含「**签名在用户设备**」，且现有流程是**用户逐笔确认**（S2 的 `/escrow create` 也是逐笔）；
- Agentic Wallets 的核心价值恰是**免逐笔授权**（在预算内自动执行"资金锁定、维护期释放"等）。

**这不是"加个功能"，而是改变"谁在什么条件下动用户的钱"**。若采纳：
- 必须明确「**代理权限一旦授予，限额内操作不可撤回**」（材料已提示）——这是**对用户的风险披露**要求；
- 提示注入攻击面扩大（材料亦提示），需与 `05` 的 Permit 钓鱼防御、`H` 节的"不制造无限授权面"约束**一并评估**；
- 与 T15/T16 的多签仲裁如何拼接，需在 S5 设计时定。

→ 建议**列为待决项**，不在未拍板前引入。
