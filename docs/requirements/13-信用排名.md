# 信用排名与定期公告（整理 + 核验）

> 来源：用户提交的信用排名设计（综合评分 / 五等级 / 周月季榜 / 隐私 / 防刷），新增 **T76–T81** 六项。
> 本文整理并做一致性核验；核验结论为整理者补充。

## 一、材料要点

**综合评分**（0–100 加权）：完成交易数 30% + 争议率（反向）25% + 好评率 20% + 交易对手多样性 15% + 账号活跃时长 10%。

**五等级**：💎 钻石（评分 ≥90 且完成 ≥50 笔）/ 🥇 金牌（≥80 且 ≥20）/ 🥈 银牌（≥70 且 ≥10）/ 🥉 铜牌（≥60 且 ≥5）/ 🌱 新手（完成 <5）。

**定期推送**：周榜（每周一 Top 10）/ 月榜（每月 1 日 Top 20 + 晋升名单）/ 季度荣誉榜。
**隐私**：排名默认脱敏（`@u***A`），用户可自选是否公开用户名。
**防刷**：互刷不计入、争议率反向、活跃时长权重、仅完成且无争议可评价。
**新增编号**：T76 综合评分 / T77 等级评定 / T78 周榜 / T79 月榜 / T80 季度榜 / T81 排名隐私控制。

## 二、核验与一致性检查（发现 5 处需澄清）

### 2.1 ⚠️ 等级条件自相矛盾：「评分 90+ 但只有 4 笔」算钻石还是新手？
钻石要求「评分 ≥90 **且** 完成 ≥50 笔」，而新手定义是「**完成 <5 笔**」。两条件在
「前 4 笔全部好评、对手各异、评分算出来 95」时冲突：按笔数是新手，按评分够钻石。
**实现前必须定优先级**（建议：**笔数门槛优先**——未满 5 笔一律新手，避免新号靠少数交易刷高评分）。

### 2.2 ⚠️ 「交易参考」与「隐私不公开」的边界未定
材料说两件可能互斥的事：① 排名默认脱敏、用户可选不公开用户名；② "用户发起交易时，**可查看对方等级和统计**"。
→ 若对方选择不公开，交易对手**还能否看到其等级与统计**？**必须明确**（建议：**交易对手可见**——
因为那是风险评估的正当需要；仅"公开榜单"脱敏。两者是不同场景，不能一刀切）。

### 2.3 ⚠️ 周榜推送与「通知模式」冲突（跨材料）
`12-通知与消息优化.md` 提出通知模式 `all` / `important`（仅最终响应与审批请求推送）。
周榜/月榜/季度榜属**非紧急内容**——若给选了 `important` 的用户推送，就**违背其偏好**。
→ 建议：榜单推送**独立开关**（默认关或并入 `all`），不能绕过通知模式。

### 2.4 ⚠️ 排名的**范围**未定：按群还是全局？
项目定位是「运营者自行部署」，一个运营者可能跑多个群。排名是**群内榜**还是**跨群全局榜**？
两者含义完全不同（跨群榜需要集中数据，且会把不同群的用户放在一起比较）。
→ 需明确；这直接影响存储设计（是否需要跨群聚合）。

### 2.5 ⚠️ 「长期稳定用户」无定义
季度荣誉榜含「长期稳定用户」，但"长期""稳定"都没有量化。→ 需给阈值（如注册 ≥180 天且期间争议率 0）。
另：「账号活跃时长 10%」也需要定义基准（从注册算？从首笔交易算？）。

## 三、与既有事项的关系（正向）

- **B3（信用分模型）从"未定"变"有提案"**：本材料第一次给出了具体模型（权重 + 阈值）。
  建议把本模型作为 B3 的**候选方案**，连同待定项（2.1/2.5）一起交你拍板。
- **与 `08` 的 1.3 一致** ✅：`08` 建议"投票人分层权重 3/2/1"，本材料说"钻石权重 3、金牌 2、银牌 1"——
  两处**取值一致**，说明同一套分层思路；建议合并为**一处定义**（投票资格与投票权重只写一遍）。
- **与 T53（互刷不累加信用）一致** ✅：材料的"互刷不计入排名"与之同义。
- **编号追加而非重排** ✅：新材料用 **T76–T81 追加**，未动 T1–T75——**符合待决 `J` 节"冻结编号"的建议**。
  这是好现象：后续材料请继续追加编号，不要重排。

## 四、项目对照

| 需要的输入 | 项目现状 |
|---|---|
| 完成交易数 / 争议率 | `TradeAdmissionContext` 有 `activeTradeCount`/`hasUnresolvedDispute`，但**无"历史完成数""争议率"聚合** → 需新查询 |
| 好评率 | `TradeReview`（T18）**已落地**（评分 1–5、仅终态可评）→ 可聚合 |
| 交易对手多样性 | T47（未实现）；`08` 也有同概念 |
| 账号活跃时长 | 无（需用户注册时间） |
| 评分/等级类 | **全部新增** |
| 榜单推送 | 依赖 S1（Bot 发送）+ 调度（G18 未实现） |

→ 结论：T76–T81 是**纯新增**，但其输入依赖**新的聚合查询**（跨 `escrow_orders` 与评价数据），
不是只加几个类就能做——需要先定**存储与聚合口径**（尤其 2.4 的范围问题）。
