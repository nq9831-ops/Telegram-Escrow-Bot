## 一、tg-group-guard 的「违禁词在线管理」（原文要点）

tg-group-guard 提供：**Web 后台实时添加/删除/启用/禁用违禁词，即时生效无需重启**。
原理是消息拦截逻辑**每次实时查询数据库**获取启用的违禁词列表。

**对项目的意义（原文）**：可增加 Web 后台管理界面，运营者实时调整词库、不重启 Bot，
用于应对突发的广告攻击（黑产突然使用新关键词）。

## 二、Gas 报告机制（原文要点）

TON 官方 Blueprint 支持 `npx blueprint test --gas-report`，生成合约 Gas 消耗报告
（含 `gasUsed`、`cells`、`bits`），并支持版本对比（`--snapshot`）。

**对项目的意义（原文）**：Tolk 合约部署后应建立 **Gas 基线**；每次逻辑变更后重新生成报告对比，
若 Gas 显著上升可及时发现。Gas 消耗直接关系**存储费池能否覆盖合约长期存储成本**。

## 三、Sola 的多进程架构（原文要点）

Sola 是生产级 Telegram 运营平台，采用 **Bot、Admin API、Web 后台、Mini App、Worker
五个独立进程**的架构，适合"长期运营、持续迭代"的产品。

**对项目的意义（原文）**：本项目定位「开发者不参与运营、运营者自行部署」；若采用多进程架构，
运营者可独立扩展（交易量大时只扩容 Worker 处理链上事件，不影响 Bot 响应）。Sola 的
Docker Compose 配置与环境变量模板可直接参考，降低部署门槛。

## 四、整理观察（补充，非原文）

### 4.1 ⚠️ 事实纠正：本项目的违禁词**不是** Trie + 缓存
原文说"你的违禁词过滤目前是 Trie 树 + 缓存"——**与源码不符**。实测
`tgg-core/src/main/java/com/tg/escrow/core/BannedWordMatcher.java`：
- **L53** 类注释原话：「**未实现 Trie / Aho-Corasick**。当前是逐词 `contains`，词表规模上千时会有性能压力」；
- **L108** `public static BannedWordMatcher compile(List<String> exactWords, List<String> regexPatterns)`
  ——**静态工厂、构造期一次性编译**，实例不可变；
- **L157** `folded.contains(entry.folded())` ——逐词子串匹配。

所以现状是：**逐词 contains + 构造期一次性编译，无 Trie、无缓存、无热更新**。
这反而说明你们的判断方向是对的——因为 `compile` 是静态的，**改词库只能重建 matcher（=重启）**，
正是"在线管理"要解决的痛点。

### 4.2 违禁词在线管理的改造方案（建议，不改匹配算法）
现状的可变点不在算法而在**词库来源**。建议**不动 `BannedWordMatcher`**（它已把正则校验、空白过滤、
大小写折叠做对了，且有测试钉住），在其上加一层**可热替换的快照持有者**：

```java
// 保持 BannedWordMatcher 不可变；新增一层 volatile 快照，原子切换 = 热更新
public final class BannedWordRegistry {
    private volatile BannedWordMatcher matcher;   // 不可变快照

    public BannedWordRegistry(BannedWordMatcher initial) { this.matcher = initial; }

    /** Web 后台改词库后调用。编译失败则保留旧快照（fail-safe，不把群暴露在"无词库"状态）。 */
    public synchronized void reload(List<String> exact, List<String> regex) {
        BannedWordMatcher next;
        try {
            next = BannedWordMatcher.compile(exact, regex);   // 非法正则会抛
        } catch (TggException ex) {
            return;                                           // 保留旧值
        }
        this.matcher = next;                                  // 原子生效
    }

    public Optional<BannedWordMatcher.Match> firstMatch(String text) {
        return matcher.firstMatch(text);
    }
}
```

要点：① 复用既有 `BannedWordMatcher.compile` 的构造期校验（**非法正则不会上线**）；
② `volatile` 引用切换保证读线程看到一致快照；③ **fail-safe**——reload 失败保留旧词库，
不因一次错误配置让过滤失效（这是安全侧的关键，与项目一贯的 fail-closed 一致）。
④ 持久化与后台接口属 Web 层，见 4.3。

### 4.3 三条材料（连同前几份）都指向**同一个结构性缺口：项目没有 Web/Admin 层**
- 本份「违禁词在线管理」→ 需要 **Web 后台 + 词库持久化**；
- `docs/requirements/03-TON-Pay与Tolk.md` 的 TON Pay webhook → 需要 **HTTP 端点**；
- 本份「五进程架构」→ 建议 **Web 后台 / Admin API / Worker 独立进程**。

`grep` 已确认项目**无任何 Web 层**（无 Spring Web 依赖、无 `@RestController`）。
这已是第五次从不同材料指向同一缺口。**建议把它收成一个显式的前置工程项**（见 4.4），
而不是每来一份材料就单独欠一笔。

### 4.4 五进程架构：方向可参考，但需先有"层"再谈"进程"
Sola 的「五进程」是**部署形态**，前提是代码里先有 **Web / Admin / Worker 的边界**。
本项目当前是**单一 Spring Boot 应用**（`tgg-app`）。
建议顺序：**先在代码里划出层**（Web 层 / 后台任务层），再决定是否拆进程部署——
否则"拆进程"只是把一个单体复制成五份，没有收益。
另注：搜索显示 Sola 有**两个仓库**——`royp888/sola`（**单 Bot 进程内置调度器**）与
`royp888/sola-bot`（**五独立进程**）。原文的"五进程"对应后者；做参考时别混。

### 4.5 Gas 报告：S5 开工即纳入，不要事后补
项目 S5 合约一行未写，现在建不了基线。建议把 **`npx blueprint test --gas-report --snapshot`**
写进 S5 的验收口径（每笔合约逻辑变更都必须出对比报告）。这与
`docs/requirements/04-x402与ENACT.md` 的 **`storageFund` 存储费池**直接相关——
Gas 与存储是同一笔成本账，"Gas 变高"可能就是"存储费池覆盖不住"的前兆。
