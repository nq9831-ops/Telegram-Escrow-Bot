# 交互细节（整理 + 核验）

> 来源：用户提交的 10 条 Telegram 交互细节建议（按钮颜色 / 加载态 / 一次性按钮 / 通知合并 /
> Mini App 主题 / 返回按钮 / 流式停止 / 仅你可见消息 / 标签适配 / 错误重试）。
> 本文整理要点并核验技术前提；核验结论为整理者补充。

## 一、十条要点与核验

| # | 建议 | 核验 |
|---|---|---|
| 1 | **按钮颜色语义化**（primary 蓝 / success 绿 / danger 红） | ✅ **真实**：Bot API 已支持按钮 `style`（2026-02-09 后的客户端才显示样式）。⚠️ 见 2.1 降级风险 |

## 二、整理观察（补充，非原文）

### 2.1 ⚠️ 按钮颜色不能是**唯一**的语义载体
核实：按钮样式只在 **2026-02-09 之后**的客户端显示（python-telegram-bot 文档原话 "Older clients will
display buttons without styling"）。因此：
- **旧客户端**用户看不到颜色；
- **色盲用户**（红绿色盲约占男性 8%）本就区分不了 success 绿 / danger 红。

→ **不能只靠颜色表达"安全 vs 危险"**。文字必须自带语义（「确认发起」vs「取消交易」），
颜色只做增强。否则在旧客户端或色盲用户那里，"危险的红色按钮"和"安全的绿色按钮"毫无区别——
这是把可访问性当装饰的典型失误。

### 2.2 第 2 条（`answerCallbackQuery`）是这批里**最该记住的实现要点**
它不是"体验优化"，而是**正确性问题**：Bot 收到 callback 后不调 `answerCallbackQuery`，
客户端会持续转圈直到超时。**S1（Bot 接线）必须把"每个 callback 都必须应答"写成不变量**，
最好用一条包装（所有 callback handler 统一先应答、再处理），从结构上杜绝遗漏。

### 2.3 第 7 条的"AI 审核结果"是**材料自带的前提错误**
本项目 V3.0 没有任何 AI/LLM 功能项，"AI 审核结果"不在需求里。这条属**材料假设了不存在的模块**——
**不纳入**（除非将来引入 AI，届时再议）。

### 2.4 这十条都是 **S1 / S6 的设计规格**，不是新功能编号
项目当前**无任何 UI 实现**（`grep` 确认无 `InlineKeyboard`/`callback`/`WebApp`/`themeParams`）。
所以这 10 条应落到：
- **S1（Bot 接线）**：第 1/2/3/4/8/9/10 条；
- **S6（Web / Mini App）**：第 5/6 条（+ 第 1 条的 Mini App 侧按钮）；
- 不新增编号——V3.0 的功能编号（G/T）里没有"交互细节"这一类。

### 2.5 与已落地能力的呼应（正向）
- 第 8 条（关键用永久、非关键用临时）↔ `08` 的 2.4 已定的同类规则；
- 第 10 条（失败给原因+可重试）↔ `TradeCommandHandler` 已实现「被拒：<原因>，可重试：<时刻>」；
- 第 3 条（一次性按钮防重复提交）↔ `EscrowOrder` 的 fail-closed 状态守卫同源（都不允许"已完成的动作再来一次"）。
