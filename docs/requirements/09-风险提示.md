# 风险提示（整理 + 逐条核验）

> 来源：用户提交的六条风险提示（预映像攻击 / Gas 费 / Mini App 兼容性 / Telegram 隐私模式 / TON 异步顺序 / 0% 费可持续性）。
> 本文整理其要点，并**逐条核验「该风险在本项目中的实际存在面」**——核验结论为整理者补充。

## 一、六条风险要点与核验

### 1. 🔐 预映像攻击（哈希可被反推）——**在本项目有对应面**
**原文**：若链上存的哈希输入空间小或可预测，攻击者可预计算常见输入的哈希再比对，从而推断原文。
建议哈希前加随机盐，或先加密再哈希。

**核验**：技术成立（字典/预计算攻击）。更关键的是——**本项目已有一处同类实现**：
`tgg-core/.../LogSanitizer.java` 的 `maskUserId(long)` 用的是**无盐** SHA-256 且**只保留 6 位 hex（24 bit）**：

```java
public static String maskUserId(long userId) {
    return USER_PREFIX + shortHash(Long.toString(userId));   // SHA-256 无盐，截 6 位 hex
}
```

两个可改进点（均**未改代码**，仅记录）：
- **无盐** → 同一 ID 在任何部署里哈希相同，攻击者可**预计算一张 userId→标识 的表**再与日志比对；
- **仅 24 bit** → 输出空间 2²⁴（约 1.7 千万），既让**暴力枚举原像**变得容易，也让**不同用户发生碰撞**
  （大用户量下两个用户显示同一标识，日志关联出错）。
- 建议：**加部署级盐值**（打成配置项，走环境变量）+ **加长输出**（如 48 bit）。
  权衡：需管理盐值（是新的配置面），且历史日志无法回溯重算——但历史日志本就不该被视为已脱敏。
- 链上 proofHash（`04`/`07` 的 T46/T47）同理：**存哈希前必须加盐**，否则"交付凭证"若是常见短语即可被反推。

### 2. ⛽ 免保证金下的 Gas 费谁出——**真实，且与 04/08 同源**
**原文**：免保证金 + 卖方无资金锁定 → 争议仲裁/投票的 Gas 由谁承担？建议预留 Gas 费池，
或争议双方预缴、败诉方承担，否则可能"争议处理到一半 Gas 不足"。

**核验**：成立，且这是**第四次**从不同材料指向同一件事（`04` 的 `storageFund` 存储费池、
`08` 的 1.1/1.6 仲裁费与平台费分离）。**建议归并成一条"费用与 Gas 谁承担"的设计项**，
不要分散在多处各自表述。

### 3. 📱 Mini App 设备兼容性——**工程常识，落到 S6 验收**
**原文**：AI 能搞定 80% 响应式设计，最后 20% 必须在真实设备/真实钱包 App/真实网络下测；
问题常只在 iPhone、MetaMask 移动版、慢速 3G 下出现。

**核验**：成立。项目 Web 层未做（结构性缺口 **S6**）→ 应写进 S6 的**验收要求**：
真实 iPhone + Android 各一台，跑完整 TON Connect 连接 → 签名 → 状态更新流程。

### 4. 🚫 Telegram 隐私模式——**最高优先，且可立即落地（纯文档）**
**原文**：Bot 在群组中**默认处于隐私模式**，只能看到命令和回复它的消息。
要看到全部消息，必须在 **BotFather 关闭隐私模式 → 移除 Bot → 重新添加**。

**核验**：成立（这是 Telegram 平台的既有行为，非新特性）。**对本项目影响重大**：
「群聊留痕」（`07` 的 T33 生命周期 / T37 证据双通道）**完全依赖 Bot 能看到所有消息**——
部署时若漏了这一步，**留痕功能静默失效**（Bot 不报错、只是看不到对话）。
→ **建议立即写进部署文档**（这是零代码成本的修复）；并在 Bot 启动时做**自检**
（如探测某条非命令消息是否可见），不可见时**告警而非静默**。

### 5. 🕐 TON 异步模型的消息顺序不可预测——**真实，且项目已有正确应对**
**原文**：TON 是异步执行模型，消息传递顺序无保证；若"确认收货"与"标记发货"几乎同时发出，
合约可能乱序收到导致状态机混乱。须为每个状态转换设计明确的前置条件检查。

**核验**：成立。**正向印证**：本项目的 `EscrowOrder` 状态机**已经**用
`requireState(State...)` 做前置守卫（fail-closed）——**非法顺序直接抛异常**，与"顺序无关"的设计一致
（见 `EscrowOrderTest` 的「fail-closed：非法迁移一律拒绝」）。**但**：
- 该守卫在 **Java 侧**已成立；**S5 的 Tolk 合约必须同样做**（每条消息处理先验前置状态）；
- 建议在 S5 验收清单里显式列一条：「乱序到达时状态机不越级迁移」。

### 6. 💰 0% 协议费的运营可持续性——**与 08 的 1.6 同源**
**原文**：平台费为 0 则运营者无收入；开源项目须在文档里说明，避免运营者部署后觉得被误导。

**核验**：成立，且已在待决 **K 节**（"平台费 0%、仲裁费仅败诉时产生"）与 **B1** 记录。
建议开源文档里**显式写一段"运营者收入模型"**（0% 是默认值、可配、可持续性由运营者自定）。

## 二、收敛（建议动作）

| 项 | 动作 | 成本 |
|---|---|---|
| 4 隐私模式 | **写进部署文档 + Bot 启动自检告警** | 低（文档 + 小自检），**优先** |
| 1 预映像 | `LogSanitizer.maskUserId` **加盐 + 加长**；链上 proofHash 也必须加盐 | 中（改已有类 + 加配置面） |

## 三、独立核验声明

- 「隐私模式」与「TON 异步无序」属 **Telegram/TON 平台既有事实**（非本材料新创），核验方式为**读项目代码
  确认依赖面**（留痕依赖全消息可见；状态机已有 fail-closed 守卫）。
- 「预映像」的技术原理成立；**项目中确实存在对应实现**（`LogSanitizer.maskUserId`，已读源码确认无盐、24 bit）。
- 「设备兼容性」「0% 费可持续性」为经验性建议，无独立可核验的技术断言。
- 本材料中未出现的项目事实（如"是否存在其他无盐哈希"）**未穷尽排查**，仅就 `LogSanitizer` 与
  链上 proofHash 两处已知点给出结论。
