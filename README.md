# TON Escrow Toolkit

> 一个通用的 Telegram 群管理 + 链上托管交易 **技术工具包**。
> 本项目只提供技术能力：不提供运营服务、不含业务参数、不含合规方案，也不针对任何特定运营主体。
>
> ⚠️ **2026-10-03 范围变更**：群管理功能已**整体移除**（管理命令/内容安全/入群风控/运维辅助全族），
> 项目现为**纯担保交易**工具包。本文中群管理相关章节**已失修**，深度清理批次待续
> （清单见 `.rivet/HANDOFF.md` 第 17 条）；保留者：**交易群**（ET-05/06/39/40）与群内 `/escrow` 命令。

> 📌 **新接手**：先读 `docs/INDEX.md`（文档地图——告诉你该读哪份、该信哪份）；
> **想直接跑起来**：`docs/QUICKSTART.md`（构建 / 测试 / 启动的最短路径）。

## 1. 这是什么，不是什么

**是**：一套可复用的技术组件——Telegram 机器人框架、群管理能力、链上托管合约、交易状态编排引擎、争议与投票流程引擎。

**不是**：一个可以直接运营的业务系统。本仓库不包含任何业务数值（费率、质押额、周期、阈值）、不含牌照与合规方案、不含运营指导。所有业务参数由部署者自行设定，并自行承担其后果。

设计原则一句话：**代码回答"能不能做到"，配置回答"允许做到什么"。**

## 当前实现状态（与蓝图的差距）

本仓库处于**能力累积阶段**。上面 §5 列的是能力蓝图，以下是它的真实完成度——写在这里是为了不让使用者按蓝图去部署然后困惑。

> **本节已于 2026-09-29 重写。** 此前版本称"没有 Bot 代码 / 应用启动即退出 / 链上只有抽象 / 配置未打通"，
> 那些描述在多个波次前即已失效。**本节也会过时**——引用具体数字前，请以
> `docs/CODE-VS-SPEC.md` 头部基线块（含可复算命令）为准，不要采信本文里的任何写死计数。

**Bot 层已接线。** 装配层按领域拆分为 `BotWiring`（核心出口链）
+ `TradeWiring`（交易/争议/信用/通知）+ `ChainWiring`（链上/钱包/部署/存证），共 49 个 bean
（2026-10-03 拆分，方法体逐字保留）：`BotDispatcher` 路由 `/escrow …`
（走 `TradeCommandHandler` → `EscrowTradeService`）、群管理命令（`/kick /ban /unban /mute /unmute /del /warn /unwarn`）、
违禁词（`BannedWordRegistry`）、内容安全处置（`MessageGuardService`：链接 → 媒体 → 可选重复检测 → 限流）。
`tgg-app` 含 Bot 长轮询与 Web 容器，**是常驻进程**——"启动后自行退出"的描述已不成立。

**交易命令清单（`/escrow` 子命令）。** `invite <金额> <币种>`（生成深链邀请，对方点开自动接单）·
`create <卖方ID> <金额> <币种>` → `confirm …`（两步流：先预览风险提示、再落单，不可跳过）·
`lock` / `deliver` / `release` / `refund` / `dispute <订单号>`（推进交易）· `status <订单号>` ·
`cancel <订单号>` · `review <订单号> <评分1-5>` · `rank [条数]`（交易榜，默认 10 条、上限 20，**默认脱敏**，
不显示完整用户 ID）· `credit`（**只查自己**的信用摘要：评分 + 等级徽标 + 五维拆解）·
`publish` / `unpublish`（ET-80：榜单公开 @username 的 opt-in / opt-out，**默认脱敏**；
无 @username 时 publish 会提示先去 Telegram 设置用户名，不落成无效开关）。

**免输 ID 的「回复式」用法（2026-10-03 起）。** Telegram 客户端不展示数字 ID——
在群里先**回复**对方的消息、再发 `/escrow create <金额> <币种>`，卖方即取被回复者，
预览回执也会引导你"回复同一条消息发 confirm"（全程不碰数字 ID）。管理命令同理：
回复某人的消息后发 `/kick`（不带 ID）即作用于被回复者，`/del`（不带消息号）删除被回复的那条消息。
显式参数优先于回复目标（同时给出时以参数为准）。

权威文案以 `TradeCommandHandler.USAGE` 为准——改命令请同步改它。

**Web 层已可用。** Mini App 端点 `/api/trade/{create,invite,accept}` 走 `initData` 验签；
`/miniapp` 提供表单页；`/admin/**`（违禁词管理、链上地址推导）已由 **Spring Security** 保护
（需 HTTP Basic；**未配置 `tgg.admin.*` 凭据时一律 401**，不是放行）。

**链上部分：provider 已落地，但未经真机验证。** jetton 钱包地址推导有已测的判定层
（`JettonWalletAddressResolver` + `TonAddresses` 的 CRC16 校验和判据），provider 为
`AdnlJettonWalletQuery`（纯 Java ADNL，免原生库；此前的 Tonlib 路线因线上加载不了 `libtonlibjson` 已删除）。
**但 `AdnlLiteClient` 的那一跳已有实测**：2026-09-29 以独立探针（复刻 `AdnlJettonWalletQuery` 的
`ownerArg → runMethod → addressFromResult`）在服务器上运行，**mainnet 已连上 liteserver**（`get_wallet_address`
返回 `exitCode=0`，解析出真实地址）、testnet 亦可连——**旧结论"从未真正连上 liteserver"已作废**。
仍未验的是**最后一跳的应用形态**：实例配上真实 `TGG_CHAIN_JETTON_MASTER` 后该端点返回 200（属部署者配置）；
`ChainSource` / `BalanceCrossVerifier` 也仍无真实数据源。

**配置面已部分打通。** `application.yml` 已绑定 `tgg.trade.*`、`tgg.pending.ttl`、`tgg.confirm.window`、`tgg.invite.ttl`、
`tgg.webapp.*`、`tgg.notify.*`、`tgg.join.*`、`tgg.protection.*`、`tgg.guard.*`、`tgg.chain.*`、
`tgg.admin.*`、`tgg.log.salt`、`tgg.warning.*`、`tgg.moderation.*`、`tgg.tonpay.*`、`tgg.welcome.template`、`tgg.trade-group.silence-days`、
`tgg.dispute.evidence-window`、`tgg.dispute.require-statements`、
`tgg.fee.*`（三费分离，默认 0 不收费；首单豁免默认开）、`tgg.risk.*`（入群风险评分，weights 留空 = 不启用）。
**注意 §6 表中那些"设计意图键名"与它们不是同一套**（那是更粗粒度的规划命名），照抄 §6 不会有任何效果。
**已落地配置键的权威清单见 `docs/CONFIG-KEYS.md`**（67 键 × 默认值/环境变量/行为说明，命令实测生成）。

**（⚠ 功能已随群管理移除——2026-10-03 起此键无代码消费者，保留供迁移期参考）原频道傀儡防御（GM-12）的开关是 `TGG_GUARD_ALLOWED_CHANNELS`**（允许以频道身份发言的频道名，逗号分隔、
忽略 `@` 前缀与大小写）。它的三个状态刻意不同：**不设该变量 = 不启用这项防御**（默认行为与从前一致）、
**设成空串 = 全拦**（空集即"谁都不许"，适合只允许个人发言的群）、**设具体名字 = 仅放行这些频道**。
未配置时把"全部频道帖"当成违规会删光群里正当的频道发言，故两者必须分开。

**入群风险评分（GM-24/25）的开关是 `TGG_RISK_WEIGHTS`**（形如 `NO_USERNAME=30,NEW_ACCOUNT=30`，
因子名取 `NO_AVATAR` / `NO_USERNAME` / `NEW_ACCOUNT` / `LANGUAGE_NOT_ALLOWED`）。**不设 = 不启用**（默认不评分、
照常欢迎）；配套阈值 `TGG_RISK_REVIEW_THRESHOLD`（默认 20）、`TGG_RISK_REJECT_THRESHOLD`（默认 50）、
`TGG_RISK_NEW_ACCOUNT_DAYS`、`TGG_RISK_ALLOWED_LANGUAGES`。命中 REJECT 会被移出；命中 REVIEW 照常欢迎、**不**在群里公开标记，只留痕，**若**配置了
`TGG_RISK_REVIEW_NOTIFY_CHAT`（管理会话 ID）则另把「待复核」**私下**投给管理员（**留空 = 不启用**，
退回只留痕；投递失败只留痕、不假装已通知）。

**信用分权重可配 `TGG_CREDIT_WEIGHTS`**（④ 差距 1；逗号分隔 5 值，顺序 = 完成数 / 争议率(反向) /
好评率 / 对手多样性(反向) / 活跃时长）。**留空 = 默认口径 `0.30,0.25,0.20,0.15,0.10`**（既有行为零漂移）；
非法值（项数≠5、项越界 [0,1]、**总和≠1**）启动期抛——分数系统性偏移比缺配置更危险，fail-fast。
配套 `TGG_CREDIT_DECAY`（④ 差距 2 轻量时间衰减；格式 `宽限天数,步长天数,每步因子,下限`，如 `365,180,0.9,0.3`）。
**留空 = 不衰减**；只作用于「活跃时长」维度，因子会写进 `/escrow credit` 的拆解文案（不静默改数）。
互刷剔除阈值复用 `TGG_FRAUD_CONCENTRATION_THRESHOLD`（默认 0.6）——评估链说"可疑"而评分链照加，
是最难查的自相矛盾，故两处**同一来源**。周榜惰性推送（④ 差距 4，ET-77）由 `TGG_CREDIT_WEEKLY_PUSH`
（默认 true）与 `TGG_CREDIT_WEEKLY_PUSH_SIZE`（默认 10）控制：**不引入调度器**，某个自然周内群里有
第一次交互时搭车推一条（每周每群最多一条，私聊不推，空榜不推）。去重状态在进程内——重启后同周可能
多推一次，这是"不做持久表"换来的已知边界。
**两个因子在生产里永远不命中且这是刻意的**：`NO_AVATAR`（需每成员一次头像 API 往返，未采集）与
`NEW_ACCOUNT`（Telegram 不暴露账号注册时间）——把它们配进权重表不会有任何效果，见
`JoinSignals` 的注释；写成未知因子名则在**启动期直接失败**。

**未接入 Redis**，因此依赖滑动窗口的能力目前是**进程内实现**（`SlidingWindowCounter` 等）：
单实例可用、多实例不共享——G6 / G23 的"Redis 滑动窗口"仍是蓝图而非现状。同理，本项目
**无调度器**，所有超时都是**惰性判定**（在命令触发或入群事件时才结算），不会自动到期执行。

已实现且**经测试覆盖**的部分：担保订单状态机（8 态 + fail-closed 守卫 + 乐观锁）、裁决多签规则与验签链路、
联邦节点 Ed25519、违禁词匹配、日志脱敏（带盐）、**入群风险评分**（信号/权重/阈值全配置驱动，默认不启用；命中 REJECT 才移出）、爆发保护 / 订阅门禁、
内容安全（链接 / **频道身份** / 媒体 / 限流 / 重复）、交易准入三规则、深链邀请、维护期与超时策略、
交易评价、应用层安全门禁、**交易者信用与榜单**（五维评分 + 等级 + 脱敏榜单，
`/escrow rank` / `/escrow credit`；仅对既有订单/评价表做聚合，未新增表）、
**订单列表 `/escrow my` 与 inline 动作按钮**（订单回执按「状态 × 角色」附此刻可执行的动作；
点击按钮只是"更友好的入口"——它解码成等价命令，走同一条权限/状态守卫链，**不是授权**）。
**逐项完成度与"是否接线"见 `docs/CODE-VS-SPEC.md`**，
**只能在真机核销的项见 `docs/ONLINE-VERIFICATION.md`**。

## 4. 架构

```mermaid
flowchart TB
    U[Telegram 用户] --> BOT[Bot 进程<br/>命令分发 / 中间件 / 权限 / 限流]
    BOT --> GM[群管理模块<br/>用户管理 / 内容安全 / 自动化 / 配置 / 反滥用]
    BOT --> TX[交易编排入口<br/>发起 / 查询 / 群创建引导 / 公告]
    TX --> WEB[Web 服务<br/>交易流程 / 状态机 / 证据 / 投票]
    WEB --> CHAIN[TON 链<br/>托管合约 / 事件监听]
    WEB --> STORE[(MySQL / Redis)]

    subgraph 部署者负责
        CFG[业务配置<br/>费率 / 周期 / 阈值 / 名单]
    end
    CFG -.-> BOT
    CFG -.-> WEB
```

分层说明：
- **Bot 层**：入口、通知、查询、群管理。**不适合承载需要实名与留痕的流程**（见 §7）。
- **Web 层**：交易流程、状态机、证据、投票。可承载需要审计留痕的流程。
- **链上层**：资金托管与事件。合约只暴露能力，不内建业务数值。
- **配置层**：所有业务决策集中于此，由部署者提供。

## 7. 渠道约束（技术事实）

Telegram Bot **无法**做到可靠的地域限制，也**无法**满足需要实名与可审计留痕的流程要求。

因此本项目的设计约定是：
- Bot 层只承担入口、通知、查询、群管理
- 需要留痕与实名的流程放在 Web 层
- 若部署者需要限制服务地域，必须在 Web 层实现，Bot 层无法代劳

这是架构约束，不是建议。

## 8. 合约接口（Tolk）

合约只暴露能力，不内建业务数值。费率、阈值、接收方、时间锁时长均来自部署时注入或治理配置。

**当前实装的是"非裁决路径"，以带 32 位操作码的内部消息触发**（定义见 `contracts/types.tolk`）：

| 消息 | 用途 | 状态 |
|---|---|---|
| `FundMessage` (`0x7d5a1001`) | 买方锁定资金（TON 或 jetton） | 已实现（含多付退回与余额守卫） |
| `DeliverMessage` (`0x7d5a1002`) | 卖方标记已交付 | 已实现 |
| `ConfirmMessage` (`0x7d5a1003`) | 买方验收 → 放款给卖方 | 已实现（TON / jetton 双路径） |
| `RefundMessage` (`0x7d5a1004`) | 退款给买方 | 已实现 |
| `JettonTransferNotification` (`0x7362d09c`) | 收认由**我方 jetton 钱包**发来的入金（TEP-74） | 已实现（含 ET-50 伪造发送者防护） |
| `onBouncedMessage` | 出账被回弹时把状态退回去 | 已实现 |

**尚未实现**：`Dispute` / `Resolve`（争议与多签裁决——待 C1 语义定案）、时间锁与紧急暂停（T21）、
可升级代理（T43）。

> ⚠️ **合约未部署**：状态机由 Acton 模拟网测试覆盖（`tests/EscrowContract.test.tolk`），
> **链上行为、Gas 与真实资金路径均未验证**。上面"已实现"指的是合约代码内已写并测，不等于已在链上跑通。

实现约束：
- 所有状态变更函数使用 `impure` 修饰符
- 减法前校验余额充足，防整数溢出
- 使用 commit-reveal 生成随机数
- 转账前校验代币发送者合约地址（`chain.trustedTokens`）

**关于可升级性（T43）**：代理合约默认不启用。可升级意味着事后可以改变资金规则，这与"合约内不保留单方提款能力"是相反方向的取舍。若部署者启用，升级权限的持有者与时间锁由部署者决定——本项目不预设。
